# More Than Yes｜不止点头

让 AI Agent 在开放式创意、产品和工程工作中，不只顺着用户的例子执行，还能核对前提、补足遗漏、比较方案，并继续完成已授权的工作。More Than Yes 是一份供宿主 AI 按需读取的协作 Skill，不是独立运行的软件，也不是让 Agent 每次都反驳用户。

核心说明可以独立使用；第一性原理、钢人论证的详细用法和正反案例随包提供，需要时再读。第一次接触它的人和 Agent 不需要知道开发时的聊天背景。

## 安装与第一次使用

将整个 `more-than-yes` 文件夹放入宿主的个人 Skill 目录，不要只复制入口文件而遗漏参考材料。以 Codex 的 `~/.agents/skills/` 为例，在 Windows PowerShell 7 中，先确认装有 Git 且没有同名文件夹，再执行：

```powershell
New-Item -ItemType Directory -Force -Path "$HOME\.agents\skills" | Out-Null
git clone https://github.com/Ww-Cooooo/more-than-yes.git "$HOME\.agents\skills\more-than-yes"
```

在 Codex 的 Skill 选择列表确认出现 “More Than Yes”；如果没有出现，重启 Codex。重启后仍看不到时，先检查 `~/.agents/skills/more-than-yes/SKILL.md` 是否存在、文件夹名称是否一致。然后在新任务中明确调用：

> 请用 $more-than-yes 和我一起评估这个方案。先检查我有没有漏掉关键前提，再给出你的判断，并继续完成已授权的部分。

观察它是否具体核对了你方案的前提、补上遗漏，并在同一任务里继续工作；这能检查一次实际表现，不能保证以后每次自动调用。其他支持 `SKILL.md` 格式的宿主也可以复制这个文件夹，但 Skill 目录、自动发现和子 Agent（被委派子任务的 Agent）的继承方式由各宿主决定。希望相关子 Agent 也采用这套方法时，在委派任务中明确写出 Skill 名称、目标和已确认边界。

### 已经安装过，怎样更新

如果按上面的 Git 克隆方式安装，先查看安装目录有没有自己的修改：

```powershell
git -C "$HOME\.agents\skills\more-than-yes" status --short
```

确认没有输出后，再更新：

```powershell
git -C "$HOME\.agents\skills\more-than-yes" pull --ff-only
```

如果列出了修改或新增文件，先保留自己的内容，再对照新版合并；如果提示无法快进更新，先处理分叉，不要强制覆盖。

如果之前是下载 ZIP 或手动复制文件夹安装，不要直接运行 `git pull`。下载完整新版，将旧包备份到 Skill 目录之外，再替换安装目录内的包文件；有个人修改时先比较并合并。更新应包含 `references/` 和 `SOURCES.md`，不能只换 `SKILL.md`。随后在新任务中明确调用一次；磁盘文件更新不等于正在进行的对话已经重新读取新版。

## 它怎样工作

- 把用户的目标、已经确定的选择、举来说明想法的例子，以及尚未证实的判断区分开。
- 对会改变结果的前提、数字和结论寻找证据；暂时查不到时明确说不确定。
- 提出有实际影响的替代方案、风险或成本，也解释用户原方案何时已经足够好。
- 在制作和复核中继续判断，而不只在回复里口头表示“我会独立思考”。
- 普通明确的小任务照常执行，不额外制造争论、长表或审批。

它是一份行为指导，不会让模型自动获得新权限，也不保证模型每次判断都正确。外部发布、覆盖、删除或其他实质操作仍由宿主与用户的权限边界决定。

## 两种方法怎样帮助判断

**第一性原理：**当关键前提可疑或方案反复失效时，回到目标、可靠事实和真实约束，区分必要条件与沿用习惯，再比较实现路径。不是每件事都推倒重来，也不让模型把自己的推测称为“基本事实”。

**钢人论证：**先忠实理解一个观点，认真考虑支持它的有力理由，再作评价。同样审查 Agent 自己的首选方案。补充理由不等于替用户编造依据，也不能把原观点换成另一套更好辩护的观点。

例如，用户说“页面加点动画，提高表单完成率”，Agent 不应直接堆动效，也不应宣称动画都没用。它应检查真正的填写障碍；如果问题在字段负担，先考虑减负，如果问题在提交后没有反馈，再让状态变化或动效承担这个职责。这个例子展示判断方法，不表示已经测出某种设计会提高完成率。

## 内容完整，但不要求每次全读

安装时取得完整包；使用时，由支持文件读取的 Agent 按任务读取相关材料。这是渐进式读取，不是执行时再下载。文件在磁盘上，不等于整包已进入模型上下文；实际加载与上下文保留方式取决于宿主，不能保证读过的内容立刻释放或所有平台都自动按需加载。

| 文件 | 内容与阅读时机 |
| --- | --- |
| [SKILL.md](SKILL.md) | Agent 启用时读取的完整基本说明，包括判断方法、必要边界及参考入口 |
| [第一性原理详解](references/first-principles.md) | 关键假设、反复失效和重新比较实现路径时读取；含完整示例与误用说明 |
| [钢人论证详解](references/steelmanning.md) | 实质分歧和重要方案比较时读取；区分原主张、补充理由与替代方案 |
| [跨场景案例](references/worked-examples.md) | 理解模糊反馈、合理方案、明确小修改、事实核验与子 Agent 交接时参考 |
| [来源与改编说明](SOURCES.md) | 人或 Agent 需要追溯理论、案例性质和许可时阅读；不是日常必读 |

README 面向安装与了解项目的读者，不要求 Agent 每个任务都重读它。入口文件已有基本协作方式；没有文件读取能力的网页聊天，可以先粘贴入口正文，需要某个方法时再补充对应材料，但这不等于已经安装或获得自动加载功能。

## 怎么判断用上了，而不是只读了几句口号

在一段不含开发历史的新对话中，给它真实任务和必要材料，观察是否指出有依据的关键问题、尊重已确认选择，并继续完成工作。也试一个方案本来就合理的请求和一个明确的小修改：它不应为了体现独立性强行反对或扩大任务。

可以查看所读取的参考文件是否与任务有关，但“读了文件”不是效果证明。判断应看交付和证据；一次任务的表现也不代表已经跨模型、跨宿主验证。仅复制本包不会让不支持 Skill 的平台自动获得这种能力。

## 文件与依赖

`SKILL.md` 与包内参考文件是核心内容；`agents/openai.yaml` 只提供 Codex 的展示名称和简短说明。本包没有可执行脚本、后台服务或收集上传对话的程序；安装命令会从 GitHub 下载文件到本机。Agent 为完成具体任务可能使用宿主已有的文件或联网工具，权限和数据处理取决于宿主与用户设置，不能因此宣称对话数据一定不离开本机。Skill 运行时不依赖另一份 Skill、特定模型、账号或第三方服务；上面的克隆安装方式需要 Git。
